# GitHub를 기준으로 하는 팀 운영

## 공용 작업 기록

저장소: https://github.com/dheorb/algorithm-study-desk

작업 보드: https://github.com/users/dheorb/projects/1

- **Issue**: 요구사항, 작업 범위, 완료 조건, 구현 주담당과 검토 담당, 선행 작업, 현재 상태.
- **Projects**: 사용자가 보는 작업 보드. 상태와 담당 역할, 연결된 PR을 표시한다.
- **PR**: 코드 변경, 검증 근거, 독립 검토와 수정 과정.
- **Orca**: 작업 공간·브랜치 준비, 에이전트 실행, 지시와 완료 보고 전달.

GitHub와 Orca는 대화 내용을 자동으로 공유하지 않는다. 총괄이 Issue 링크를 명시해 배정하고, 에이전트는 시작할 때 최신 Issue와 이 규칙을 읽는다. Issue가 있다는 이유만으로 에이전트가 자동 실행되지는 않는다. 별도 상시 감시 프로세스는 사용하지 않는다.

사용자는 총괄에게 자연어로 요청하면 된다. 총괄은 사용자에게 같은 내용을 Issue에 다시 쓰도록 요구하지 않는다. 필요한 결정이 빠졌으면 확인하고, 확보된 범위의 작업을 정리한다.

## 기능별 전담과 실제 인수

[Issue #13](https://github.com/dheorb/algorithm-study-desk/issues/13)의 사용자 요청으로 모든 기능을 한 구현자가 순차 처리하던 방식에서 기능별 전담과 필요 시 병렬 개발로 전환한다. 기존 총괄 Run을 유지하며 AI 담당은 기존 창/공간을 이어 쓰고, 코드 편집기 담당은 별도 Codex 창/공간을 사용한다. 과거 동일 구현·검토 두 창만 재사용하던 지시는 당시 기록이며 현재의 추가 배치를 일괄 금지하지 않는다. 각 배정에서 명시한 생성 권한과 범위는 그대로 따른다.

책임 영역·작업창 표시 이름·공간/브랜치·확인 시점·인수 근거는 [담당자 현황](team-owners.md)에 분리해 기록한다. 역할을 정의했다고 작업자가 생성된 것은 아니며, 생성·착수만으로 코드 인수가 끝난 것도 아니다. 기존 담당도 인수 기준 SHA·읽은 파일·접점·검증 방법·한계를 Issue 댓글로 남긴다. 운영 문서 작성은 이번 Issue에서 AI 담당에게 임시 배정했으며 모든 도메인의 상시 구현 책임을 뜻하지 않는다.

총괄은 같은 도메인의 후속 작업에 기존 담당을 우선 배정한다. 새 영역, 별도 전문성 또는 독립 검증/병합할 수 있는 작업이 필요하면 추가 담당을 배치하고 이유·범위를 Issue에 남긴다. 학습 데이터·추천과 앱 기반·실행 자동화는 현재 책임만 정의했고 실제 전담자는 미배정이다. 관련 기능 Issue를 시작할 때 배치하며 기존 AI/편집기 담당에게 자동으로 넘기지 않는다.

## 병렬 작업과 공유 계약

독립 검증과 병합이 가능한 작업은 **별도 Issue·작업공간·브랜치·PR**에서 병렬로 진행한다. 파일이 다르더라도 같은 문제 선택/초안/저장 상태를 바꾸면 독립이라고 단정하지 않는다. 여러 도메인에 걸치는 요구는 하위 Issue로 나누고 아래 항목을 구현 전에 합의한다.

| 배정에 기록할 항목 | 결정 책임 |
| --- | --- |
| 도메인 담당, 실제 구현 주담당 한 명, 독립 검토자 | 총괄 |
| 실제 공간·브랜치·기준 SHA, 재사용 또는 추가 배치 이유 | 총괄과 배정 담당 |
| 공개 인터페이스의 입력/출력·오류·상태 소유·호환성 | 소비/제공 도메인 담당 제안, 총괄 확정 |
| 공유 접점별 실제 작성자·선행 Issue/PR·병합 순서 | 총괄 |
| 통합 책임자와 각 PR/통합 후 검증, 미확인 범위 | 총괄과 검토 담당 |

`renderer.js`/`index.html`/`styles.css`는 공통 화면 연결, `main.cjs`/`preload.cjs`는 IPC·생명주기, `store.cjs`는 공통 저장 기반이다. ChatStore도 이 기반을 상속한다. 기본 책임은 변경 요청 창구이지 다른 전문가의 편집을 금지하는 소유권이 아니다. 전문가가 공유 변경을 요청하면 총괄이 그 Issue의 작성자와 계약을 정한다. 같은 동작을 동시에 바꾸는 PR은 병합 순서를 명시하고, 다른 담당의 작업 브랜치를 직접 덮거나 미커밋 변경을 임의로 stash/reset하지 않는다.

선행 PR이 병합되면 남은 담당은 자신의 변경을 보존한 채 최신 기준을 반영하고 계약 차이·충돌을 총괄과 해결한다. 기준 SHA와 영향 검증을 PR에 갱신한다. 충돌이 없다는 사실만으로 통합 동작이 검증된 것은 아니다. 총괄이 지정한 통합 책임자는 최종 사용자 흐름을 확인하고 검토자는 최신 head의 근거를 남긴다.

병렬 UI/저장 시험은 각 작업의 합성 `/tmp`와 `STUDY_DESK_DATA_DIR`, 시험 프로세스를 분리한다. 담당은 자신이 만든 시험 자식만 정리하며 다른 창의 앱·데이터를 종료/수정하지 않는다. 제품 변경의 영향에 맞게 단위·Electron·마이그레이션·실패 경계를 선택한다. 문서만 바뀌면 링크/구조/문법/diff를 검증하고 무관한 Electron·모델 호출을 반복하지 않지만 최신 head의 필수 GitHub CI는 생략하지 않는다.

결정·인터페이스·검증 자료는 Issue/PR/저장소에 남겨 새 담당이 재구성할 수 있게 한다. 전체 채팅이 자동 전달됐다고 가정하지 않는다. 재개할 때 총괄은 실제 Orca 세션/공간을 조회해 역할 연결을 확인한다. handle·Task/Dispatch 같은 일시적인 식별자를 영구 주소로 취급하거나 공개 명단에 불필요하게 복사하지 않는다. 공개 문서에는 안정된 역할명·공간/브랜치·인수 댓글·확인 시점을 우선 쓴다.

## 예시: 로그인 후 앱 자동실행과 매일 3문제 추천

이는 향후 기능을 나누는 **설계 예시이며 이번 문서 작업에서 구현하거나 활성화하지 않는다**.

| 하위 작업 | 책임과 합의할 결과 |
| --- | --- |
| 출처/정규화·추천 | 데이터·추천 담당을 배치하고 문제 식별자·날짜·추천 근거·부족/실패 상태의 결과 계약을 정의 |
| 앱 시작·스케줄·전달 | 앱 기반·실행 자동화 담당을 배치하고 중복 실행 방지·저장·IPC 전달 계약을 정의 |
| 결과 표시·문제 선택 | 총괄이 실제 UI 연결 작성자를 명시하고 표시 상태/선택 문제 계약을 구현 |
| 편집기·AI 연동 | 기존 담당은 선택 문제 계약의 소비자로 참여하고 편집 상태/전송 맥락 영향을 검증 |

날짜 경계·재시도·오프라인·문제 부족 정책은 미래 기능 Issue에서 결정한다. 개발 에이전트는 배정된 때 코드를 만드는 주체이고 앱의 자동실행/스케줄러는 별도 런타임 기능이다. 개발 창을 유지하거나 이 문서를 작성했다고 앱 자동실행이 설치되는 것은 아니다. `process-supervisor.cjs`는 **Codex AI 요청의 취소·deadline·수명 관리**이며 일반 앱 자동실행 담당으로 옮기지 않는다.

## 작업 한 개의 흐름

1. 총괄은 요구를 독립적으로 검증할 수 있는 작은 Issue로 나눈다. 큰 요청은 상위 Issue의 체크리스트로 묶고 선행 Issue를 링크한다. 단순 질문은 개발 Issue로 만들지 않는다.
2. 총괄은 **배정 전에** Issue를 작성하고 보드에 추가한다. 도메인 담당·실제 구현 주담당 한 명·별도 검토 담당, 공간/브랜치/기준 SHA, 범위 밖·완료 조건, 공개 인터페이스·선행 Issue·병합 순서를 기록한다. 아직 정해지지 않은 요구를 임의로 구현하지 않는다.
3. 총괄은 Orca로 작업 공간과 브랜치를 준비한다. 같은 도메인 후속 담당을 우선 재사용하고 필요 시 추가 배치하며, 독립 작업은 공간·브랜치·PR을 분리한다. 배정 메시지에는 Issue URL, 역할, 수정 범위, 완료 조건과 보고 방법을 넣는다. Orca 작업 공간에 `reference add`로 Issue를 연결한다.
4. 구현 담당은 최신 Issue를 읽고 시작을 보고한다. 작업 브랜치에서 변경을 커밋·푸시하고 Issue와 연결한 PR을 만든다. 긴 작업은 Draft PR로 중간 결과를 공유할 수 있다. 막힌 이유와 다음 행동도 보고한다.
5. 검토 담당은 Issue와 PR의 **현재 head SHA**를 읽고 독립적으로 검증한다. 결과에 SHA, 실행한 확인, 미확인 범위, 필수 수정 여부를 기록한다. 제품 코드는 수정하지 않고 구현 담당에게 수정 요청을 돌린다. 추가 커밋이 생기면 그 변경에 영향을 받는 검토를 갱신한다.
6. 총괄은 최신 head의 필수 CI `unit-tests` 통과, 로컬 검증, 독립 검토와 미해결 필수 수정을 확인한다. 조건이 충족되면 PR로 main에 병합한다. Issue 전체 완료 조건이 충족됐을 때만 Issue를 닫고 보드를 완료로 바꾼다. 사용자에게 사용 방법·검증·남은 제한과 링크를 보고한다.

구현·푸시는 결과 제출이고, PR 생성은 검토 요청이다. 최종 완료는 검토·병합·완료 조건 충족까지 포함한다. main에 직접 푸시하거나 과거 커밋 이력을 강제로 바꾸지 않는다. 초기 로컬 이력 업로드만 이 규칙 도입 전 기준점이다.

## 상태와 갱신 책임

총괄이 상태의 최종 관리 책임을 가진다. 작업자는 **시작, 막힘, PR 제출, 검토 결과**를 보고하고 GitHub에 근거를 남긴다. 총괄은 해당 보고를 받는 턴에 Issue 상태 라벨·Projects 상태·Orca 작업공간 상태를 함께 갱신한다. 채팅에만 완료를 남기지 않는다.

| 의미 | Issue 라벨 | 보드 Status | 갱신 시점 |
|---|---|---|---|
| 대기 | `status:todo` | Todo | Issue 등록, 배정 준비 |
| 진행 중 | `status:in-progress` | In Progress | 담당자의 작업 시작 보고 |
| 검토 중 | `status:review` | Review | 검토 가능한 PR 제출 |
| 막힘 | `status:blocked` | Blocked | 선행 작업·정보·권한 등으로 진행 불가 |
| 완료 | `status:done` | Done | 병합 및 Issue 완료 조건 충족 |

상태 라벨은 한 개만 유지한다. `type:*` 같은 다른 라벨은 보존한다. Issue 본문의 현재 상태에는 다음 행동을 기록하고, 막힘에는 이유와 해결 담당을 적는다. 검토에서 수정이 필요하면 진행 중으로 되돌리고 같은 PR에 추가 커밋한다.

보드 동기화에 실패하면 Issue 댓글에 실제 상태·실패 원인·다음 행동을 남기고 해결 후 보드를 맞춘다. 확인하지 못한 상태를 성공으로 표시하지 않는다. GitHub에 작업 정의를 기록하지 못하면 새 구현을 배정하지 않는다. 작업 중 일시 장애가 생기면 현재 로컬 변경을 보존하고 보고한다.

### 보드 갱신 방법

공개된 프로젝트·필드·상태 ID는 [github-project.json](github-project.json)에 있다. 인증정보가 아니며, 보드를 다시 만들거나 옵션을 바꾸면 실제 API 값으로 갱신한다. GitHub CLI의 `project` 권한이 필요하다.

1. `gh project item-add 1 --owner dheorb --url <Issue 또는 PR URL> --format json`으로 추가하고 반환된 item `id`를 사용한다. 이미 있는 항목인지 확실하지 않으면 먼저 `gh project item-list 1 --owner dheorb --format json`으로 확인한다.
2. `gh project item-edit --project-id <project id> --id <item id> --field-id <status field id> --single-select-option-id <status option id>`로 상태를 지정한다.
3. 같은 `item-edit`에서 `--field-id`에 담당 또는 다음 행동 필드 ID를 넣고 `--text`로 내용을 갱신한다.
4. Issue의 기존 `status:*` 라벨만 교체하고, 보드의 실제 상태를 다시 읽어 확인한다. PR을 별도 카드로 추가했으면 그 카드도 갱신한다.

GitHub Projects의 내장 이벤트 자동화만으로 에이전트 배정·시작·막힘을 알 수는 없다. 이 구성에서는 총괄의 보고 처리 단계가 상태 동기화를 수행한다. 보드 카드의 담당 역할·다음 행동과 연결된 PR을 사용자가 직접 볼 수 있다.

## 에이전트 역할과 GitHub 계정

현재 GitHub 사용자 계정은 `dheorb`를 사용한다. 에이전트의 이름은 별도 GitHub 사용자 계정이 아니다. Issue의 담당 역할, 보드의 담당 필드, 브랜치와 PR 설명으로 역할을 구분한다.

검토 댓글은 `검토 담당 · 대상 커밋 <SHA>`로 시작한다. 같은 계정이 만든 PR에는 자기 자신의 정식 Approve를 시도하지 않는다. 독립 에이전트의 검토 근거와 GitHub의 계정 기반 승인 요건은 구분한다. 별도 사용자 계정의 승인 수를 요구하는 설정은 이 구성에 넣지 않는다.

## 자동 검증과 병합

현재 GitHub Actions의 필수 확인은 `unit-tests`다. Linux Node 22에서 `npm ci` 후 `npm test`를 실행하며 저장 계층과 대화 상태·프로토콜의 단위 동작을 검증한다. 실제 Codex 모델 요청과 설치 CLI 도구 경계 시험은 별도 로컬 검증이다. Electron 화면·프로세스 재시작·한글 입력까지 검증했다고 보고하지 않는다. UI·저장 동작에 영향을 주는 변경은 PR에서 해당 통합·수동 검증 근거를 추가한다.

현재 main 보호 규칙은 PR 경유, 최신 main 기준 `unit-tests` 통과(`strict: true`, GitHub Actions app ID `15368`), 검토 대화 해결을 요구한다. 관리자에게도 적용하며 강제 푸시와 브랜치 삭제를 허용하지 않는다. 정식 승인 수는 0으로 두되 독립 에이전트의 검토 근거는 위 운영 규칙으로 확인한다. 계정·서비스 제한으로 CI가 실행되지 못한 경우도 통과로 취급하지 않는다. CI 없는 병합 예외는 종료됐으므로 추가 문서 커밋도 최신 head의 필수 검사를 확인한다.

총괄은 보고에 적힌 커밋이 PR의 최신 head와 같은지 확인한 뒤 병합한다. PR이 Issue의 모든 완료 조건을 충족하면 `Closes #번호`로 연결해 main 병합 시 종료할 수 있다. 일부만 해결하면 `Refs #번호`로 연결하고 Issue를 열어 둔다. 병합 직후 Issue·보드가 실제로 완료됐는지 확인한다.

### 2026-11-16 사용자 승인 CI 임시 예외 — 종료된 기록

계정 제한으로 GitHub Actions가 실행되지 않아, 사용자가 지원 답변을 기다리는 동안 CI 통과 없이 병합할 수 있도록 요청했다. [Issue #4](https://github.com/dheorb/algorithm-study-desk/issues/4)의 임시 운영 기간에는 main의 `unit-tests` 필수 조건만 해제했다. PR 경유, 관리자 적용, 검토 대화 해결, 강제 푸시·브랜치 삭제 금지는 그대로 유지했다.

당시 총괄은 병합할 최신 head의 로컬 `npm test` 결과와 변경에 필요한 추가 검증, 독립 검토를 확인하고 PR에 대상 SHA·실제 결과·미확인 범위를 남겼다. CI workflow는 유지했으며 실행되지 않은 CI를 통과로 표시하지 않았다. 이 예외는 전체 개발 사이클의 CI 검증 완료를 뜻하지 않았다. PR #3/#6/#8의 과거 실행 전 failure와 당시 병합 기록은 이번 복구로 소급 변경하지 않는다.

2026-11-16 총괄은 PR #10 제출 head `0f239793d3c46ea04934b315b1cbb2e98d7fd67b`의 [CI run 43837068177 / unit-tests](https://github.com/dheorb/algorithm-study-desk/actions/runs/43837068177/job/133196238511)가 실제 `npm ci`·`npm test`까지 completed/success임을 직접 확인했다. 이에 따라 필수 조건을 `strict: true`, `checks: [{"context":"unit-tests","app_id":15368}]`로 복구했고, **복구 즉시 CI 없는 병합 예외를 종료했다**.

검사가 해제된 상태여서 `PATCH .../protection/required_status_checks`는 `404 Required status checks not enabled`를 반환했다. 총괄은 현재 전체 보호 설정을 보존한 `PUT .../branches/main/protection`에서 required_status_checks만 복구했다. `contexts`와 `checks` 동시 지정은 422였으므로 `checks`만 지정했다. 최종 GET 및 공개 감사 자료의 before/after 비교에서 위 필수 검사와 **나머지 모든 보호 필드의 불변**을 확인했다. 구체적인 절차와 근거는 [Issue #4](https://github.com/dheorb/algorithm-study-desk/issues/4)에 있으며, 공개 설정 감사 파일은 `/tmp/study-desk-ci-restore-vt9z0xoc/`에 보관했다.

복구 당시에는 Issue #4의 문서 반영·독립 확인·최종 최신 head CI·정상 병합과 기록/보드 반영을 마칠 때까지 열어 두도록 했다. 이후 #4는 완료됐으며 이 절은 종료된 과거 절차를 보존한다. 제출 head의 성공만으로 이후 문서 커밋의 CI까지 통과했다고 간주하지 않는다. 보호 설정은 이미 복구됐으며 이 문서 변경에서 재설정하지 않는다.

## 총괄의 배정 메시지 예시

> Issue: 해당 GitHub Issue URL
>
> 도메인 / 실제 구현 주담당 한 명 / 독립 검토자: 배정한 역할
>
> 공간·브랜치·기준 SHA: 실제 값
>
> 공유 접점 작성자·입출력/오류/상태 계약·선행 Issue/병합 순서·통합 책임: 실제 합의 또는 없음
>
> 먼저 최신 Issue와 AGENTS.md, docs/team-workflow.md를 읽는다.
>
> 수정은 지정 작업 공간·브랜치에서 한다. 범위가 바뀌면 구현 전 총괄에게 알린다.
>
> 시작·막힘·PR 제출 시 보고한다. PR에는 변경 이유, 검증, 미확인 사항을 기록한다.
>
> 감독 작업자라면 기존 Task/Dispatch 지시에 따라 worker_done으로 결과·PR URL·head SHA를 보낸다.

## 이전 기록

첫 기능은 GitHub 연결 전에 로컬에서 구현·검토·병합했다. 기존 커밋과 보고서를 그대로 보존하며, 과거 작업을 GitHub PR로 검토했던 것처럼 재구성하지 않는다. `docs/coordination-handoff.md`의 과거 실행 식별자는 역사적 기록이고 현재 연결의 증거로 쓰지 않는다. 재개 시 Orca에서 현재 세션과 주소를 다시 확인한다.
